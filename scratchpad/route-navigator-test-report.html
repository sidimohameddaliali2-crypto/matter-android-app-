Methodology

Three separate kinds of checking went into this, kept distinct below rather than blended into one "looks fine" verdict:

1. Executed tests — the route maths (distance, bearing, nearest-point-on-route) and the server's polyline decoder run as real Jest / Node test suites below, with their actual terminal output. These are hard results, not estimates.

2. Code trace — the stateful parts (GPS watch timing, phase transitions, button gating) can't run without React Native and a GPS chip, so each scenario below is a manual step-by-step trace against the actual committed code, citing exactly what was read. This is where the one real bug turned up.

3. Needs a live device — map tile rendering, the native blue-dot location marker, and real GPS hardware behaviour can only be confirmed by actually driving with the app open. Flagged explicitly at the end rather than assumed to be fine.

2 · Bug found during this review

Route stayed stale after completing a stop

Found & fixed

What was wrong: the screen tried to detect "the driver just completed this stop" by checking whether the current stop's ID appeared in a completed-deliveries list. Tracing the actual render order showed that check could never be true — by the time a stop is marked complete, it has already been filtered out of the screen's own stop list, so it can never simultaneously be "the current stop" and "in the completed list" in the same render.

Effect: the map kept showing the route line to the just-finished stop, and if the "Arrived" screen was still open when the next stop's data arrived, it would start showing the next customer's name while the screen still said "Arrived" — before the driver had actually gotten there.

Fix: track the current stop's identity directly in a ref instead. Whenever it changes while mid-route, reset to the driving phase and fetch a fresh route for whatever stop is now active — works the same regardless of whether the stop was completed through this screen or from the Deliveries tab directly.

RouteNavigatorScreen.js — replaced the completed-IDs check with an activeStopIdRef identity-change effect. Also removed activeIndex/doneStopIds state, which turned out to be unreachable for the same reason.

3 · Scenario walkthroughs

Each traced against the committed code, with the real timing constants it actually uses.

Permission & first GPS fix

Verified by trace
  1. t=0 Screen mounts, requests foreground location permission.
  2. Denied → full-screen "Location permission needed", no map ever renders.
  3. Granted → one GPS fix requested, raced against a 12,000 ms timeout.
  4. Fix arrives in time (typical outdoors: 1–3s) → "Start route" enables.
  5. No fix within 12s (weak/indoor signal) → red error text + Retry button, not an infinite spinner.
Expected: the button never hangs on "Getting your location…" forever, in either failure mode.

Idle overview, before starting

Verified by trace
  1. Today's pending deliveries filtered to those with GPS coordinates, sorted by stop number (falls back to scheduled time).
  2. t=300ms after mount, camera fits all stop pins with asymmetric padding (more room at the bottom, under the sheet).
  3. Zero routable stops → dedicated empty state, distinct from "route complete".
Expected: an overview of the whole day's route before committing to "Start".

Tapping "Start route"

Verified by trace
  1. t=0 Phase → driving. Camera mode → car.
  2. Camera animates to the driver's position immediately: 60° pitch, zoom 17, 450ms — called directly here, not left to a reactive effect that could lag a render behind.
  3. Directions requested for just the single next stop (not the whole day), bounded by the API client's 15,000 ms timeout.
  4. Success → route polyline drawn, instruction banner appears. Failure/timeout → red pill, no stale line left on screen.
Expected: the driver-mode camera tilt happens on the tap itself, not sometime after.

Driving — live tracking

Verified by trace
  1. GPS watch: Balanced accuracy, fires on whichever comes first — 4,000 ms elapsed or 15 m moved.
  2. Heading from the device's own compass/course when available; falls back to bearing-between-fixes otherwise.
  3. Camera re-centers on every fix while in car mode — in practice, roughly every 4 seconds, more often if moving fast.
  4. Instruction banner picks the step whose cumulative distance hasn't yet been passed, with a matching left/right/u-turn/straight icon from Google's own manoeuvre code.
Expected: a smooth-feeling follow camera without hammering the GPS chip or the directions API.

25m arrival gate

Verified by trace
  1. Distance to the active stop recomputed on every GPS fix (Haversine — the exact formula checked in the executed tests above).
  2. >25m away: "I've arrived" disabled, label shows live "Get closer (Xm away)".
  3. ≤25m: button enables.
  4. GPS watch deliberately kept alive through the Arrived phase too (not just Driving) — otherwise this distance would freeze at whatever it was the instant "arrived" was tapped.
  5. "Scan bags & complete" carries the same 25m gate — if the driver drifts off before completing, a message explains why instead of silently blocking the button.
Expected: physically impossible to complete a delivery from somewhere else.

Resync after completion (the fixed bug, re-traced)

Verified by trace
  1. Driver completes stop A, taps "Back to deliveries" → lands on Deliveries > list, which re-fetches the driver's deliveries.
  2. That fetch updates the one shared Redux store both tabs read from — Route tab is still mounted in the background and re-renders immediately, with A now excluded and B as the new active stop.
  3. Identity-change effect notices B ≠ A, resets phase to Driving, fetches B's route.
  4. Driver switches back to the Route tab: already showing B, not stale data for A.
  5. If A was the last stop: phase → Done instead.
Expected: correct next stop and fresh route every time, regardless of which screen completed the delivery.
